# 《灵魂匹配局：社区 × 社交》产品说明计划书

> **一句话**：把斯坦福小镇（Generative Agents）的方法论搬进一个由知乎内容驱动的实时多人世界——让数字分身拥有持久记忆、能相遇交谈、会替主人探索知识与表达观点。

---

## 摘要

- **做什么**：一个知乎主题的数字分身小镇。内容空间化为六栋建筑，观点人格化为数字分身，阅读—讨论—理解—表达被串成一条可行走、可回访的连续体验。
- **技术主张**：不做「套壳聊天窗口」，而是复刻 Generative Agents 的**记忆流 / 检索 / 反思 / 规划 / 社交**五件套，并针对真实 MMO、LLM 成本、数据权限三个现实约束重新工程化。
- **两个核心系统**：
  - **长期记忆**：Mem0 语义层 + SQLite 结构层的两级记忆，按 `avatar:{id}` / `pair:{a}-{b}` 作用域严格隔离，全程可降级；
  - **LangGraph Agent Loop**：ReAct 工具调用，工具权限按「主人 / 访客」收窄（11 / 4），身份不进入模型上下文，会话经 SqliteSaver 跨重启延续。
- **现状**：世界、知乎公共能力、Agent 对话、长期记忆、托管挂机、通讯录与远程通讯、PvP 动作战斗均已跑通；个人知乎数据与内容生产链路属于下一阶段（OAuth 已就绪）。

---

## 一、项目概述

「灵魂匹配局：社区 × 社交」是一个知乎数字分身社区原型：以 RPGJS 多人小镇作为可视化入口，以 FastAPI + 知乎开放平台能力作为知识与创作服务，以 Agent 与长期记忆作为分身的表达与关系引擎。

用户不是从一组孤立 API 或聊天窗口开始，而是进入一个由知乎内容主题组织起来的世界：在热榜广场发现正在发生的议题，在藏书阁检索资料，在问道馆获得回答线索，在创作坊形成选题和草稿，在知我居认识自己的兴趣、人设与分身。项目希望探索一种新的知乎内容消费与创作方式：让「阅读—讨论—理解—表达」成为可持续的社交体验。

**为什么是这个形态**：斯坦福 Generative Agents 证明了「一群有记忆、会反思、能计划的 LLM 智能体」可以涌现出可信的社区行为。知乎恰好具备这套实验所需的全部燃料——真实议题、真实创作者、真实关系与观点。我们要验证的不是「AI 能不能聊天」，而是**「AI 分身能不能在一个持续存在的世界里代表一个真实的人，积累记忆、形成关系，并把知识带回社区」**。

## 二、创作背景与问题定义

知乎社区积累了海量问题、回答、文章与专业经验，但用户在传统信息流中容易停留在单次浏览：看见热点，却未必找到可靠材料；有了想法，却难以组织成自己的表达；认识了观点相近的人，却缺少低门槛、具象、可持续的交流场景。

本项目聚焦三个问题：

1. 如何把知乎内容发现从「刷信息」转化为有目标的探索与对话？
2. 如何降低从阅读、提问到创作的转化成本，让用户更容易形成自己的观点？
3. 如何让数字分身不只是一次性问答，而能保留人设、偏好与共同记忆的连续性？

## 三、核心创作思路

项目的核心不是把知乎页面搬进游戏，而是把知乎社区中的**知识关系**映射为**空间关系**与**主体关系**：

- **内容空间化**：六栋功能建筑承载不同的知识行为——热榜（公共议题入口）、藏书阁（资料检索）、问道馆（问题理解）、创作坊（表达生产）、知我居（个人分身）、天工坊（结构化材料生产，规划中）。
- **观点人格化**：每个玩家与居民都对应一个带兴趣、表达风格和记忆的数字分身。对话不只返回答案，也呈现立场、语气与关系的变化。
- **创作过程化**：从热榜或搜索发现主题，经直答与资料整理形成理解，再由 Agent 协助生成知乎风格草稿；草稿保留人工修改与继续讨论的空间，绝不自动发布。
- **多人关系化**：在线玩家、常驻居民与托管分身共享同一世界；偶遇、交流与再次见面沉淀为关系与记忆，形成比单次工具调用更有连续性的社区体验。

## 四、技术架构总览

```text
┌──────────────────────── 浏览器（RPGJS Client）────────────────────────┐
│  地图渲染 / 输入 / 地标与对话面板 / 战斗表现                          │
└──────────────┬───────────────────────────────────────┬────────────────┘
               │ WebSocket（token 校验）               │ HTTP（Bearer 会话）
               ▼                                       ▼
┌── RPGJS Node Server（世界权威）────────────┐  ┌── FastAPI（大脑）──────────────────┐
│  地图 / 碰撞 / 移动判定 / 多人房间同步    │  │  知乎 Tool Registry（11/4 工具权限）│
│  托管分身状态机（巡游 / 到达 / 相遇）     │  │  LangGraph ReAct Agent Loop         │
│  在线租约 / 断线清理                      │  │  Mem0 语义记忆 + SQLite 结构化记忆  │
└───────────────────────────────────────────┘  │  OAuth 边界 / 人设冷启动            │
                                               └────────────────────────────────────┘
```

**架构原则**

1. **世界权威与知识权威分离**：游戏世界需要高频、确定性、可回滚的物理与房间状态；知识推理需要低频、可降级、可替换的模型调用。两者共进程会让一次 LLM 抖动拖慢整个世界。FastAPI 不保存地图/房间/移动状态，RPGJS 不接触任何凭证。
2. **身份在服务端闭环**：WS 升级阶段以 token 向 FastAPI 校验并重写 `avatar_id`，业务接口从 token 解析用户，客户端传入的 ID 只作为回退兼容，不作为权限依据。
3. **实验能力可降级**：记忆、模型、知乎凭证任意一项缺失或异常，核心世界与基础对话都不被阻断（详见六、七章）。
4. **可替换性**：知乎能力经共享领域模型 + Provider（HTTP / 官方 MCP）抽象；Agent Loop 与前端通过契约协作，未来可替换前端或接入其他 Agent Runtime。

## 五、从 Generative Agents 到知我境

斯坦福论文的五个构件，在本项目中被逐一映射为可工程化的模块，并针对真实约束做了取舍：

| Generative Agents 机制 | 本项目实现 | 工程取舍与原因 |
|---|---|---|
| **记忆流**：带时间戳的自然语言记录 | Mem0 向量库（嵌入式 Qdrant + 本地 `bge-small-zh-v1.5`）+ `episodes` 结构化事件表 | 中文短文本本地嵌入，免外部 embedding 费用与网络依赖；结构化字段可审计、可回放 |
| **检索**：近因 × 重要度 × 相关度 加权 | 作用域过滤 + 近因排序 + 语义检索；主人读私有记忆与最近 5 位伙伴的 pair 记忆 | 暂不做重要度评分模型；先保证**隔离正确**与**成本可预测**，把评分列为路线图 |
| **反思**：周期性高层洞察 | 会话结束一次结构化摘要（`summary/topics/mood/familiarity_delta/relation_tag`）；主人对话每 6 条提炼 `facts/prefs/todos` | 单次 LLM 调用产出 JSON；内容哈希幂等；失败只记日志、不阻塞对话 |
| **规划**：日计划递归分解 | `/api/agent/step` 每 ≥30 秒返回一个高层意图（`move` / `say` / `idle`） | 移动交给 RPGJS 本地状态机执行，**LLM 不参与逐帧控制**；模型不可用时降级为确定性巡游 |
| **社交**：对话、关系、信息传播 | 2 格内相遇触发交谈，写入 pair 记忆并双向更新熟悉度/关系标签 | 60 秒/对冷却 + 全局并发闸门，防止「社交风暴」击穿成本 |

**与斯坦福的三个本质差异**

1. **真实时 MMO，而非离线仿真**：真人与托管分身共处一个世界，移动、战斗、断线都必须由服务端权威判定；斯坦福没有网络时钟与并发写入问题。
2. **成本硬约束**：斯坦福可以不计代价跑一整个小镇的问题；我们必须给每个分身预算——30 秒决策间隔、5 秒模型超时、15/30/60 秒退避、进程级并发上限 3、相遇冷却 60 秒。
3. **权限与隐私边界**：斯坦福的 Agent 只与彼此说话；我们的分身要代表主人访问知乎数据，因此必须引入工具权限收窄、记忆作用域隔离与 OAuth 最小授权。

**我们刻意简化了什么（诚实清单）**：暂无重要度评分的结构化反思循环（当前是会话级摘要）、暂无日计划式的多层规划、暂无长时间线的关系演化与信息传播模拟。这些不是遗忘，而是把「先跑通隔离与成本」放在「先像论文」之前——路线图见第十三章。

## 六、长期记忆系统：可隔离、可审计、可降级

### 6.1 两级作用域

记忆按两个作用域写入与读取，权限由**服务端**按数值 ID 判定：

```text
avatar:{id}          主人私有：事实 / 偏好 / 待办；仅本人分身可读
pair:{min}-{max}     双方共享：共同经历与关系变化；仅这两个身份可读（ID 排序保证唯一）
```

隐私规则：主人与自己的分身对话时读取私有记忆，并按 `relationships.last_met_at` 读取最近不超过 5 位伙伴的 pair 记忆；与其他分身对话只读取对应 pair。注入 prompt 的内容总量约 1200 字符，人设卡约 300 字符。`/api/agent/step` 只为最近的一个对象读取 pair，绝不枚举私有作用域。

### 6.2 写入路径

| 事件 | 频率 | 产物 | 写入方式 |
|---|---|---|---|
| 主人 ↔ 自己分身 | 每累计 6 条消息 | `facts / prefs / todos` | `infer=true` 写入 private，更新 profile 与 episode |
| 访客 / 相遇对话 | 每轮回复 | `summary / topics / mood / familiarity_delta / relation_tag` | `infer=false` 写入 pair，双向更新关系、追加 episode |
| 知乎人设冷启动 | 手动触发（OAuth 后可自动化） | 兴趣领域 / 表达风格 / 观点摘要 / 兴趣标签 | 单次 LLM 抽取，幂等写入 `persona_cards` |

交流内容哈希作为幂等键，重复写入不产生脏数据；关系字段（熟悉度、双方视角的 note 与 tags、最后见面时间）与记忆同步落库，使「记得住」与「说得清」互为审计。

### 6.3 存储分层

- **Mem0（嵌入式 Qdrant）**：语义检索层，负责「记得住」；
- **SQLite 结构化表**：`avatar_profiles`（人设事实）、`relationships`（有方向的熟悉度与标签）、`episodes`（scope + 摘要 + 时间线），负责「说得清、可回放」；
- **`persona_cards`**：知乎数据冷启动的人设卡，独立于记忆开关（不受 `MEMORY_ENABLED` 影响）；
- **LangGraph checkpoint**：会话状态落在 `MEMORY_DATA_DIR` 下的 SQLite，进程重启后 `conversation_id` 延续。

选型上我们评估过 Graphiti（时序知识图谱，需 Neo4j 级运维）、Zep（商业托管）、LangMem（持久化偏 Postgres）、MemOS 等方案：没有开箱即用且贴合「社交关系语义」的库，因此采用 **Mem0 做事件/事实层 + 自建关系结构**的组合，并在需要时以 `sqlite-vec` 升级语义检索。

### 6.4 降级与运维

| 变量 | 默认 | 说明 |
|---|---|---|
| `MEMORY_ENABLED` | `1` | 设为 `0` 完全关闭，回到无长期记忆行为 |
| `MEMORY_DATA_DIR` | `./memory_data` | Qdrant、history 与 LangGraph checkpoint 路径 |
| `MEMORY_EMBEDDER` | `fastembed` | `fastembed` 本地模型或 `openai` |
| `MEMORY_EMBEDDER_MODEL` | `BAAI/bge-small-zh-v1.5` | 本地中文 embedding 模型 |

`mem0ai` / `fastembed` / `onnxruntime` 均为惰性导入：未安装、初始化失败或运行时读写异常时只记录日志并降级，chat 与 step 的主要响应不被阻断。依赖版本全部固定（`mem0ai==2.0.20`、`fastembed==0.8.0` 等），保证本地与线上行为一致。

## 七、LangGraph Agent Loop：带权限的工具调用

### 7.1 运行时

`/api/agent/chat` 每次请求按目标分身的人设启动一个 LangGraph ReAct Agent：

```text
用户消息 ──► create_react_agent(LLM, tools, system_prompt, checkpointer)
                ├─ tools 来自知乎 Tool Registry，经 StructuredTool 适配
                ├─ checkpointer = SqliteSaver（conversation_id 跨重启延续）
                └─ 回复后异步写入记忆（见第六章），失败不影响响应
```

系统提示词由三部分组成：分身人设（简介/兴趣/表达风格）、经过权限过滤的记忆上下文、人设卡摘要（≤300 字符）。模型默认走 OpenAI 兼容接口（`deepseek-v4-flash`），4 秒超时、不自动重试，把重试决策留给上层。

### 7.2 工具权限

| 工具组 | 数量 | 内容 | 主人 | 访客 |
|---|---|---|---|---|
| 公共内容 | 4 | 热榜、知乎搜索、全网搜索、问题推荐 | ✅ | ✅ |
| 创作能力 | 2 | 知乎直答、草稿生成 | ✅ | ❌ |
| 个人数据 | 5 | 本人内容、关注、收藏、收藏夹、创作统计 | ✅ | ❌ |

`ToolContext.user_id` 只由宿主注入，**不出现在模型可见的工具参数中**——模型没有任何途径伪造身份或越权读取知乎数据。同一份 Tool Registry 同时服务 REST 接口与 Agent 工具，避免两套实现产生行为差异。

### 7.3 双契约：chat 与 step

- `chat`：整段回复，用于主人对话、访客对话与相遇交谈；
- `step`：单步 JSON 意图（`move` / `say` / `idle`），用于托管分身的世界行为；只接受位置、附近对象、地点表与上一动作，返回确定性的结构化动作。

### 7.4 错误分类与成本控制

Agent 运行时把模型异常映射为稳定的错误码与可重试语义：`LLM_NOT_CONFIGURED`、`LLM_AUTH_FAILED`、`LLM_RATE_LIMITED`（429）、`LLM_UNAVAILABLE`（503）、`LLM_UPSTREAM_ERROR`（502）、`LLM_INVALID_RESPONSE`（502）。世界侧据此选择退避重试、降级巡游或提示用户。

成本策略：每分身 ≥30 秒一次决策、5 秒超时、15/30/60 秒指数退避、进程级并发上限 3、相遇 60 秒冷却、pair 记忆 Top-5 注入。我们的目标是让「一个持续运行的世界」在单台 2C4G 服务器上可控地久跑。

## 八、与知乎社区生态的契合度

- **内容生态**：热榜、搜索、问题推荐与直答成为世界中的公共事件与探索入口，议题来自真实社区而非编造。
- **创作者生态**：选题 → 参考资料 → 草稿生成，帮助用户从阅读者变为回答者/作者；产品**不自动发布**，尊重作者最终编辑权。
- **知识质量**：公共内容与全网内容分开检索与呈现，保留来源链接；直答用于快速获得综合线索，深度研究回到原始来源。
- **用户关系**：以兴趣与观点为基础促成分身交流，强调「因内容相遇」，而非泛化的陌生人社交。
- **开放平台边界**：公共能力由服务端统一封装；个人数据经 OAuth 明确授权后按最小范围读取；App ID / App Key / Access Secret / OAuth Token 四类凭证严格区分，浏览器永不接触。

对知乎的潜在价值：提供一种更有沉浸感的内容发现入口，延长高质量内容的讨论链路，降低参与创作的门槛，并为未来的知识 Agent 与创作者工具提供可验证的交互样本。

## 九、产品功能与场景

### 9.1 当前小镇

64×48 格连续地图，六栋可交互建筑（热榜广场、知我居、藏书阁、问道馆、创作坊、天工坊）与南侧环路。建筑面板统一展示 `ready / unconfigured / auth_required / coming_soon` 状态，不把未接通能力伪装成可用。

### 9.2 四个核心场景

- **场景 A · 从热点进入问题探索**：热榜 → 搜索 / 直答 → 与附近分身讨论不同看法；
- **场景 B · 从想法形成草稿**：创作坊输入想法 → 选择回答/文章与语气 → Agent 结合人设与参考材料生成结构化草稿 → 继续追问修订；
- **场景 C · 认识自己的分身**：知我居触发知乎数据冷启动（需授权），生成可查看、可刷新的兴趣/风格/观点人设卡；
- **场景 D · 持续的分身社交**：靠近在线玩家或居民发起对话，记忆按私有/共享隔离，再次相遇时交流具有连续性。

### 9.3 世界交互

托管挂机（`G` 切换 / 一动接管）、相遇交谈、通讯录与远程消息（离线分身代答、连续自动回复上限 5 条、主人回复即清零）、PvP 动作战斗 v2（连击 / 闪避 / 格挡 / 蓄力 / 软索敌，带头顶血条与倒地复活）。

## 十、安全与合规

- 凭证只存在于服务端或部署平台 Secret：本地 `~/.config/zhiwojing/secrets.env`、线上 `/etc/zhihu.env`（600）；不写入源码、日志、前端或命令行参数；
- 身份在服务端闭环：Session token 只存 SHA-256，30 天过期；WS 升级时校验并重写身份；`AUTH_REQUIRED=1` 时未认证连接直接被拒；
- 记忆与服务端判定：作用域由数值 ID 决定，客户端 ID 不作为权限依据；
- 个人数据最小读取：关注仅作兴趣信号，不自动建立联系人；
- 草稿默认不自动发布；日志不记录密钥与回调敏感参数；
- 游客账号每日 04:00 清理（可关闭），避免实验数据无限增长。

## 十一、创新点与项目价值

1. **生成式智能体的真实 MMO 化**：把 Generative Agents 的记忆流/反思/规划/社交拆解为可运行的工程模块，并首次与真实在线玩家共享同一世界（真人、托管分身、常驻居民同场）。
2. **可隔离的两级长期记忆**：`avatar` / `pair` 作用域 + Mem0 语义层 + SQLite 结构层 + 幂等写入 + 人设冷启动，用工程手段同时满足隐私、成本与可审计。
3. **带权限的 Agent 工具调用**：11 / 4 工具收窄、身份不进模型上下文、ToolContext 服务端注入，让「分身替人办事」具备可用性而不仅是可玩性。
4. **面向成本的持续世界设计**：30 秒决策、并发闸门、退避与确定性降级，使一个常驻 LLM 世界可以在普通服务器上长期运行。
5. **可替换架构**：世界权威与知识权威分离，Provider 可切换（HTTP / 官方 MCP），为接入更多知乎能力与未来 Agent Runtime 留出空间。

## 十二、当前 MVP 与验证情况

**已完成**：多人 RPGJS 世界与连续地图；六栋建筑与地标交互；知乎公共内容 Tool Registry（热榜/搜索/全网搜索/问题推荐/直答/草稿）；Agent 对话与行为意图双契约；人设冷启动；两级长期记忆；托管挂机与相遇；通讯录与远程消息；游客与知乎 OAuth 双登录（含 WS 身份校验）；PvP 动作战斗 v2。

**验证方式**：

- 后端单元测试 75 项（输入校验、鉴权、记忆隔离与幂等、通讯、OAuth 契约、知乎接口）；
- 前端单元测试（含 12 项战斗逻辑）与生产构建；
- Playwright 真机双客户端 smoke：命中与双端 HP 同步、聊天输入聚焦保护、闪避无敌窗口；
- 增量验证：移动/地图契约、地标交互、桌面与窄屏浏览器走查。

**已知边界**：托管仅在页面在线时有效（无离线常驻实体）；个人知乎数据与正式 OAuth 回跳需在部署环境验收；连击/格挡/招架/蓄力与远端血条视觉目前为逻辑级覆盖，手感待真机试玩调参；藏书阁知识库、天工坊 PDF/PPT 生产、技能栏与状态效果属于后续阶段。

## 十三、版本规划

- **阶段一（当前 MVP）**：多人小镇、公共知乎能力、Agent 对话、长期记忆与托管社交。
- **阶段二（个人化）**：完成知乎 OAuth 正式链路，接入本人创作、关注、收藏与创作统计，人设冷启动自动化。
- **阶段三（世界深化）**：常驻居民 Agent 化（NPC 转为永久挂机玩家）、关系与恩怨记忆、社交日报、离线持续存在。
- **阶段四（创作增强）**：回答/文章生产链路、引用与草稿编辑、单篇创作统计。
- **阶段五（知识生产）**：藏书阁知识库、天工坊 PDF/PPT 异步生成与下载。
- **阶段六（生成式智能体完整度）**：重要度评分与结构化反思循环、多层日计划、信息传播与社区治理。
